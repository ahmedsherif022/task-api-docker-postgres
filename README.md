# Task API

A simple **CRUD REST API** for managing a to-do list, built with **Python + FastAPI**.
Tasks are stored in **Postgres** with Docker persistence — data survives server restarts.

This project demonstrates the power of layered architecture: the same service and route code works
with an in-memory store **or** a real Postgres database. Only the repository implementation changes.

Interactive documentation (Swagger UI) is auto-generated by FastAPI at `/docs`.

## Quick start (local, without Docker)

```bash
pip install fastapi uvicorn python-dotenv
cp .env.example .env   # edit if needed
python -m pip install psycopg2-binary
uvicorn main:app --reload
```

Then open:

- http://localhost:8000/docs — interactive Swagger UI (try the whole CRUD cycle here)
- http://localhost:8000/ — API info

> **Windows PowerShell users:** `curl` in PowerShell is an alias for `Invoke-WebRequest`.
> Use `curl.exe` instead, e.g. `curl.exe -i http://localhost:8000/tasks`.

## Run with Docker Compose

Start the whole stack (Postgres + app) with one command:

```bash
docker compose up --build
```

The app will be available at http://localhost:8000/docs.

## Architecture — switching storage changes only one file

The service (`main.py`) and routes are **completely unchanged** when swapping storage.
The abstraction lives in `repositories.py`:

- `TaskRepository` — interface (abstract base class)
- `PostgresTaskRepository` — real implementation using psycopg2

To use in-memory (original behavior): the old `tasks = [...]` list is commented out in `main.py`.
To use Postgres: `PostgresTaskRepository` is instantiated with the connection string from `.env`.

**This means: your service code, routes, and API contract are identical regardless of storage.**

## Endpoints

| Method | Path             | Description                        | Success | Error codes |
|--------|------------------|------------------------------------|---------|-------------|
| GET    | `/`              | API name, version, endpoint map    | 200     | —           |
| GET    | `/health`        | Liveness check (`{"status":"ok"}`) | 200     | —           |
| GET    | `/tasks`         | List all tasks                     | 200     | —           |
| GET    | `/tasks/{id}`    | Get one task                       | 200     | 404         |
| POST   | `/tasks`         | Create a task (`title` required)   | 201     | 400, 422    |
| PUT    | `/tasks/{id}`    | Update `title` and/or `done`       | 200     | 400, 404    |
| DELETE | `/tasks/{id}`    | Delete a task (empty body)         | 204     | 404         |

### Business rules (validation)

- `POST /tasks` with a missing/empty `title` → `400` `{"detail": "Title cannot be empty"}`
- `PUT /tasks/{id}` only changes the fields you send; an empty/whitespace `title` → `400`
- Unknown id on GET/PUT/DELETE → `404` `{"detail": "Task 99 not found"}`
- `DELETE` returns `204 No Content` with **no response body**

## Persistence — proof that data survives a restart

1. Start the stack: `docker compose up --build`
2. Create a new task:
   ```bash
   curl -i -X POST http://localhost:8000/tasks -H "Content-Type: application/json" -d '{"title": "Task that survives restart"}'
   ```
3. Note the returned `id`.
4. Stop the app: `Ctrl+C` (stop the container, not just the process)
5. Restart the app: `docker compose up --build`
6. Verify the task is still there:
   ```bash
   curl http://localhost:8000/tasks/{id}
   ```
7. The task persists — this is because `pg_data` volume retains data across container restarts.

Without a volume, Postgres data would disappear when the container restarts. The `docker-compose.yml`
declares a named volume `pg_data` mounted at `/var/lib/postgresql/data`, ensuring persistence.

## Tech notes

- FastAPI auto-generates the OpenAPI spec and Swagger UI from the code — zero extra config.
- `TaskCreate` / `TaskUpdate` are **Pydantic models**: request bodies are parsed and type-checked automatically (`422` on invalid shape).
- The repository pattern decouples the API from the storage layer — swap SQLite → Postgres by changing **one file** (`repositories.py`) and adding `.env`.
- Connection string lives in `.env`, which is gitignored; `.env.example` is committed so teammates know the format.
